## Method

All variants ran on the same Linux x86-64 VM with the same frozen benchmark
checkout, corpus, upstream C pin, harness, compiler flags, and native process
scope. The harness uses `time.perf_counter_ns()` around a native process with an
internal loop of 10,000 parses, five warmups, and 30 measured repetitions.
Process startup is included and not subtracted. The six valid fixtures were:

`tiny_04_arr`, `tiny_03_pair`, `tiny_02_empty_arr`, `tiny_05_string`,
`tiny_06_bool_null`, and `tiny_01_empty_obj`.

The exact order for each compiler was `--verify-only`, `--smoke`, then `--full`.
All three compiler points passed correctness on all six fixtures. The full JSON
outputs and logs are retained under
`results/jsmn-post-p8-20260814/{historical,pre-p8,post-p8}/`.

## External C comparison

The primary comparator is C GCC O2. Geometric means use only fixtures valid for
all variants in the comparison.

| S3 point | S3 O1 ns/parse geomean | S3 O1 / C O2 |
| --- | ---: | ---: |
| historical | 6357.409 | 48.82x |
| pre-P8 | 7091.481 | 41.54x |
| post-P8 | 6842.710 | 39.88x |

Post-P8 remains a large external gap: the best fixture is `26.31x` slower than
C O2 and the worst is `66.75x` slower. The post-P8 S3 O1 absolute geomean is
`3.508%` lower than pre-P8, while the S3 O1/C O2 geomean ratio is `4.017%`
lower. This is classified as a modest external improvement, not a claim that
P8 was validated by this benchmark.

## Structural effect

A separate no-timing assembly probe used the same six fixtures at O0/O1 and
counted the native `cmp byte ptr [rbp...], 0` initialization-check pattern.
This is independent structural evidence, not a dynamic event count.

| Metric, six fixtures at O0/O1 | Pre-P8 | Post-P8 | Delta |
| --- | ---: | ---: | ---: |
| initialization-check pattern | 23172 | 22812 | -360 |
| static instructions | 587952 | 586152 | -1800 |
| branches | 151992 | 151272 | -720 |
| loads/stores | 295500 | 294780 | -720 |
| stack operations | 88794 | 88434 | -360 |

The generated S3 O1 native binary changed from `1141256` to `1137144` file
bytes and from `1133647` to `1128655` `.text` bytes. These structural changes
are modest relative to the remaining runtime gap.

## External bottleneck candidates

These are inputs for later research, not a P9 selection:

1. **Initialization and memory-state materialization.** The external assembly
   probe observes a real but small reduction in initialization checks, branches,
   loads/stores, and stack operations. It does not establish dynamic hotness or
   prove that this is the dominant runtime cause.
2. **Fixed-array, frame traffic, and representation expansion.** The post-P8
   S3 O1 code remains tens of times slower than C O2 with substantial static
   load/store and stack surfaces. This is a measured structural symptom; the
   benchmark does not isolate its causal subcomponents.
3. **Per-parse fixed-cost expansion.** S3 O1 remains near S3 O0 on the full
   JSMN workload, suggesting that this harness's dominant cost is not fully
   removed by current optimization selection. This is a low-to-moderate
   confidence hypothesis because the benchmark has no phase-level attribution.
